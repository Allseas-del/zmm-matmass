Part A – Functional design

1. Purpose and scope

Materials delivered in the SAP Migration Cockpit (LTMC) template for the migration object Product are created (and optionally changed) in S/4HANA through SAP's released OData V4 Product API, from a browser-based tool that runs as an app in the Fiori launchpad. The engine is the one built and tested for the STIHL maintenance task list upload (API_MAINTENANCETASKLIST, v1.0, 24 Sep 2026).

In scopeDetails
Create materialsBasic data, descriptions, plant, storage location, valuation, sales and other views – as far as the template sheets have an entity in the API (chapter 5).
Change materialsChange mode reads the existing material and PATCHes only the fields that differ; missing sub-entities (e.g. an extra plant) are added.
Custom fieldsZZ1_*_PRD fields on MARA, if enabled for the V4 API in the Custom Fields app (open point).
Volume$batch per chunk ("split"), parallel workers, results file and resume.
Out of scopeReason
MDG change requestsDecision 25 Sep 2026: materials are created directly through the API; MDG governance is bypassed for this load.
Deleting materialsDeletion flag via standard transactions.
Template sheets without API entityReported in the log and not sent (list follows with the mapping).

2. Solution overview

Fiori launchpad tile → BSP application ZMMMATMASS (UI5 component that hosts the self-contained upload tool in a same-origin frame) → OData V4 Product API on the same host. Because the app is served by the SAP system itself, there is no CORS issue and no console loader: the tool uses the launchpad session of the user.

3. Process

  1. Open the tile Material Master Mass Upload.
  2. Test connection – reads CSRF token, $metadata, effective user.
  3. Load the filled LTMC template (XML Spreadsheet 2003); check / edit the grid per sheet.
  4. Dry run – validates every payload against $metadata.
  5. Execute – create or change; progress per material.
  6. Download results (CSV) and full log; resume from results after an interruption.

4. User interface

Same layout as the task list tool: Connection, File, Data (editable grid per sheet, max. 500 rows shown, filter on material), Execute, Log. Connection is reduced to sap-client and service path; host and logon come from the launchpad.

6. Create mode and change mode

Create: POST the product root, then the child entities per sheet in $batch chunks with the key returned by SAP. Change: read the product with its children, PATCH only differing fields, POST missing children.

7. Error handling, results and restart

Per step, never per run. Status per material: done, partial (root exists, some children failed – complete with Change), failed (nothing in SAP). Results CSV: source key → SAP material number, status, failed children, message.

8. Authorizations

8.1 Who can start the app

Users whose role contains the launchpad catalog with tile/target mapping Material-massUpload (catalog, group/space and role: open point). The tile only makes the app visible; it grants no data access.

8.3 Where the protection sits

All authorization and data checks are in SAP. The tool cannot bypass them; changes are recorded under the launchpad user. Because the load bypasses MDG, the role with S_START on the Product service should be restricted to the migration team (decision data owner).

9. Constraints and assumptions

  • Product V4 service group published in /IWFND/V4_ADMIN on DS4/QS4/PS4; virus scan profile /IWBEP/V4/ODATA_UPLOAD active (note 3027559).
  • Referenced master data (plants, storage locations, material types, units, sales orgs) exists.
  • Units: the API expects the external code in the user's logon language (finding on STIHL); unit mapping in the tool.

Part B – Technical design

10. Architecture

ObjectContent
BSP ZMMMATMASSUI5 component (Component.js, manifest.json) + tool.html (vanilla JS, no libraries). Deployed with npm run deploy (deploy-to-abap, DS4/400, ZMM_MATMASS, DS4K915674).
LaunchpadInbound Material-massUpload; catalog / target mapping open.
Engine (reused)SpreadsheetML parser, index, mapper, $metadata validator, HTTP layer (CSRF, logon-page detection, $batch with odata.continue-on-error, resend of unprocessed rest), worker pool, results/resume.

11. API usage

Service definition API_PRODUCT_2, version 0001 (namespace com.sap.gateway.srvd_a2x.api_product_2.v0001), OData V4, formats JSON. Service path: to be confirmed (URL that returned the $metadata). $batch with odata.continue-on-error as in the task list tool; each product and its children are sent as one unit, products in parallel workers.

12. Volume

Chunk size ("split") and parallel workers configurable; to be measured with ~100 materials in DS4/410.
