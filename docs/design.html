Part A – Functional design

1. Purpose and scope

Materials delivered in the SAP Migration Cockpit (LTMC) template for migration object Product are created or changed in S/4HANA through SAP's released OData V4 Product API (API_PRODUCT_2). The tool is the engine built and tested for the STIHL maintenance task list upload, adapted to the product business object and hosted as an app in the Allseas Fiori launchpad instead of being started from the browser console.

In scopeDetails
Create materialsBasic data (incl. custom fields ZZ1_*_PRD), descriptions, units of measure with GTINs, procurement/sales/storage/QM views, plant data with all plant views, storage locations, MRP areas, inspection setup, valuation, distribution chains and sales tax classification.
Change materialsReads the product from SAP, sends only differing fields and adds missing plants, storage locations, units etc. – all changes of one product in one atomic change set.
VolumeSelection is split into $batch packages, several packages in parallel, results file and resume.
Out of scopeReason
MDG change requestsDecision 25 Sep 2026: materials are created directly through the API; MDG governance is bypassed for this load.
Deleting dataDeletable=false on product, plant, valuation, sales entities. Deletion flags (IsMarkedForDeletion) can be set with Change mode if added to the mapping.
Classification, characteristics, retail/fashion sheets, classic WM, ledger valuation sheetsNo entity in API_PRODUCT_2 (list in chapter 5.4). Rows are reported in the log and not sent.

2. Solution overview

The page contains no SAP logic. Every check that decides whether a material is valid (material type, plant, valuation class, units, authorizations) is done by SAP's product business object behind the API.

3. Process

#StepWhat the user does / sees
1StartTile Material Master Mass Upload. The tool tests the connection itself: service reachable, custom fields in the service, SAP user.
2Load fileChoose the filled template. Rows per sheet are shown; sheets without API entity and orphan rows are reported.
3Check / editGrid per sheet; the sub-line of each column shows the API property. Changed cells turn yellow and can be saved back into the template.
4Dry runValidates every product against the live $metadata (property exists, not computed, length, decimals, type, identifying fields filled) and shows the payload of the first three.
5ExecuteCreate or Change. Progress line: products processed, ok/errors, throughput, remaining time.
6ResultsDownload results (CSV) and full log. Failed products: correct data, run again (done products are skipped automatically).
7RestartAfter an interruption: load template and results CSV; done products are deselected.

5. Data: template and mapping

5.1 Template

Input is the Migration Cockpit template Product as downloaded from SAP (XML Spreadsheet 2003, 28 sheets). The tool identifies each sheet by its structure name (row 4) and field names (row 5); data starts in row 9. Child rows are linked to the product by PRODUCT, plant-dependent rows additionally by WERKS, GTINs by MEINH.

The file as downloaded from SAP is not well-formed XML: it starts with a line break before <?xml and the introduction sheet contains SAP text markup (<LS>…</>). Excel accepts this, a browser XML parser does not. The tool removes both before parsing (unit test 03).

5.3 Rules

RuleImplementation
UnitsAll template units are ISO codes and are sent to the …ISOUnit properties (e.g. MEINS → BaseISOUnit, MEINH → AlternativeISOUnit). No conversion table.
TypesConverted from the live $metadata: Decimal/Int → number (decimal comma accepted), Boolean ← X/true/1, Date → YYYY-MM-DD, IsUpperCase → upper case, IsDigitSequence → leading zeros. Empty cells are never sent.
Custom fieldsZZ1_CROSS_REF_PRD, ZZ1_MAKERSUPPLIER_PRD (→ ZZ1_MakerSupplier_PRD), ZZ1_MATRL_PRD, ZZ1_MFRPN_PRD, ZZ1_NMOD_PRD, ZZ1_SERNP_PRD (Boolean), ZZ1_WNFI_PRD on Product. ZZ1_MFRPN_PRD was added to the V4 service on 25 Sep 2026 (confirmed in $metadata). A template field whose property is not in the service is reported and skipped.
DescriptionsMAKTX/SPRAS of Basic Data and the rows of Additional Descriptions are merged per language.
GTINsAdditional GTINs are attached to the unit of measure with the same MEINH; the consecutive number is assigned 00001, 00002 … per unit.
Tax classificationMLAN is per country only, the API keeps sales tax per sales organization/distribution channel. Each MLAN row (TATYP1..9/TAXM1..9) is sent under every distribution chain of the product (to be confirmed in integration test). Without a distribution chain the rows cannot be sent.
Material number"Send product number from the file" (default on) sends PRODUCT (Product is Immutable, not Computed). Off: SAP assigns the number; it is returned in the results.

6. Create and change

ModeRequests per productBehaviour
Create – deep insert (default)1 POST Product with all compositions, inside a $batch packageAtomic per product: created completely or not at all.
Create – step-wisePOST Product (basic data), then GET with $expand and one change set with PATCH (1:1 views that SAP creates implicitly) and POST via navigation (plants, units, valuations …)Fallback if DS4 rejects the deep insert. If the change set fails, the product exists with basic data only (status partial) and is completed with Change.
ChangeGET Product('X')?$expand=…, then one change setOnly fields that differ are sent; missing children are created; children in SAP that are not in the file are left alone. Atomic per product.

ETag: all entities share the product's LastChangeDateTime. The first PATCH of a change set carries the ETag read by the GET, the following ones If-Match: * (the first change already moves the timestamp; the change set is atomic, so the concurrency check stays effective).

7. Errors, results and restart

Errors are handled per product, never per run. A product ends as done, failed (nothing in SAP) or partial (step-wise create: basic data in SAP, views not). SAP's message is shown per product and in the results CSV (src;product;status;steps;message). When SAP returns a logon page (session expired), the run stops starting new work and the log explains how to resume.

12. Volume ("split")

The selection is cut into packages of Products per $batch (default 20); Parallel requests (default 4) packages are in flight at the same time. Each product in a package is an independent request, so one rejected product does not affect the others. Real throughput depends on SAP's processing time per product; to be measured with ~100 materials in DS4/410 before a full load.

13. Client-side processing

Nothing is stored in the browser. Results and log live in memory until downloaded. The grid shows max. 500 rows (filter on product), the log the last 800 lines (full log downloadable).
